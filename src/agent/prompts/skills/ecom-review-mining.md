# 差评 → 卖点反向链路

**竞品的差评就是你的产品需求清单。**"给产品写一段好听的文案"价值有限；
"从竞品差评里挖出买家真实抱怨，转化成本品的卖点与微创新方向"才是这条
链路的价值所在。方向：差评主题 → 需求真伪验证 → 卖点/需求映射 → 事实
锁定后进文案。

## 第一步：A/B 对照采集（严禁随机抓）

评论采集必须围绕功能/痛点定向选品，随机抓畅销品评论文本命中率极低：

| 组 | 选品标准 | 回答的问题 |
|----|----------|------------|
| A 类：已带该功能/痛点的产品 | 用功能关键词定向搜 2-3 个真实在售品 | 买家对这个功能真实评价如何（好评提到？吐槽没用？） |
| B 类：同品类不带该功能的头部竞品 | 品类 Best Seller 里选 2-3 个 | 有没有人抱怨"缺了这个功能"（wish it had 类反向需求） |

每组每个品目标 15-30 条评论、总量 ≥80 条；ASIN 必须是真实可验证的
10 位编号，严禁占位符。

## 第二步：信号阈值判定

**Review 维度**（对 A/B 两组分别统计）：

| 信号 | 条件 | 解读 |
|------|------|------|
| 🟢 强信号 | 功能提及率 >10%，或需求表达 ≥5 条 | 买家明确在意 |
| 🟡 弱信号 | 提及率 3-10%，或需求表达 1-4 条 | 有信号不强烈 |
| 🔴 无信号 | 提及率 <3% 且无需求表达 | 买家不关心 |
| ⚠️ 负面信号 | 功能相关评论里负面 >60% | 功能有需求但现有实现差——改进型机会 |

需求表达信号词库：wish it had / would be nice if / if only / missing /
needs a / 期望类中文表达。

**三维交叉验证**（有条件时叠加，防"感觉有需求"）：

| 维度 | 看什么 |
|------|--------|
| Review | 上表阈值 |
| 关键词 | 该功能词有无真实搜索行为；无数据不得当有数据下结论 |
| 社区 | 相关讨论量与态度；**搜索结果为零也是有效信号** |

综合矩阵：三维皆正=强真需求（可作核心卖点）；两维=弱真（承认风险）；
一维=待验证（别大投入）；无正面或有负面=伪需求。特殊情况：关键词无
信号+评论强=市场教育不足型（可先发但要教育成本）；关键词有+评论负面=
现有实现差（改进后可做）。

## 第三步：投诉 → 卖点转化

1. 投诉按 **频率 × 严重度** 排序（退货触发型 > 使用体验型）。
2. 每个高频投诉主题问一次：本品**真实具备**对应特性吗？
   - 具备 → 可写成卖点（Bullet 里直接回应："不会像竞品那样 X"式表达要
     客观、不点名竞品）；
   - 不具备 → 只能进产品改进需求清单，**绝不能写进文案**。
3. 差评里的买家原话是最好的关键词来源——提取高频用词进搜索词候选。

## 本项目数据边界（降级链，诚实执行）

本项目的工具现状决定可用信号层级，逐级降级并如实标注，**缺哪层就报哪层**：

1. **语料库信号（可用）**：`search_amazon` 返回竞品的 rating 与
   review_count——低分+高评论数=高风险竞品（痛点已被大量买家验证）；
   高分+高评论数=品类标杆。此为代理信号，不等价于评论文本分析。
2. **评论证据包（需用户提供）**：语料库无评论文本。要做真正的差评主题
   分析时，向用户索要评论导出（CSV/文本，含 ASIN、星级、日期、正文），
   拿到后按 A/B 分组、按阈值表统计。
3. **关键词/社区维度**：当前无联网搜索工具——缺数据时结论标注"未验证"
   并降低信心等级，**不编造搜索量、不虚构评论、不伪造引语**。

负面信号必须写入结论；所有判定引用具体数据（提及率、条数、评分），
不允许"用户普遍反映"式空泛表述。
